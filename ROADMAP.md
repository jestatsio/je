# je roadmap and settled decisions

**Status. Final.** Started November 4, 2026. Marked Final by Eric on November 4, 2026. Q1 through Q26 are settled.

**How to use this document.** We step through the questions one at a time, starting at Q1. Each question comes with choices, a recommendation, and the reasoning behind it. Accept the recommendation, pick another option, or change the question. Each settled answer gets recorded here before we move to the next one.

## Where je stands today

Two repositories carry the work.

| Repository | What it holds |
| --- | --- |
| [jestatsio/je](https://github.com/jestatsio/je) (public) | This repo. The documentation site, the native Codex and Claude Code plugins, and the downloadable releases. |
| jestatsio/jestudio (private) | The source. About 14,900 lines of Python, 1,171 tests passing at the last recorded run on November 3, plus the memory service, the workspace machinery, and 34 design and results documents. |

The installed user client is `je` 0.2.0. It ships as a standalone Homebrew build that carries its own runtime. Today that user build is a connection launcher. It saves named model and memory profiles, checks them without running inference, and opens Codex, Claude Code, or the native Ollama CLI with a chosen profile. It does not yet run a prompt itself, choose a model for a task, or manage the local inference stack.

Around the user client, the private repo already holds working Studio host and source-side pieces. A memory service built on Mem0, Qdrant, and SQLite serves the same records over MCP and a browser page, with edit history and a 30-day trash. A workspace system runs per-owner Lima virtual machines under Coder, with a network policy compiler and guarded startup. A LiteLLM and Ollama gateway serves local models, and Open WebUI provides browser chat. Task-history event preparation with secret redaction is built, though storage stays off until erasure in backups works end to end. These service and operator components are not modules inside the standalone user build.

One honest limit matters for every question below. The small 4B model used in the local trials did not qualify for real coding work in either harness. The final fast and strong models still need selection and qualification on the Studio hardware.

## Already settled

Eric confirmed these points on November 2 and 3, 2026, in the Mac Studio launch plan. They stay in force unless a question below reopens one on purpose.

- The hardware is an M5 Ultra Mac Studio with 512 GB of memory, arriving December 10 to 17, 2026. It stays in one place on a stable home or office network.
- The launch audience is two to three trusted people, with one or two active at once. Workloads are coding, research, documents, and data analysis.
- Local models come in two selectable tiers, one fast and one stronger. Cloud models stay bring-your-own and explicitly chosen. There is no automatic cloud fallback.
- Memory is shared across tools, editable by its owner, and separated per person. Deleted memories sit in trash for 30 days and then leave every copy, including backups.
- Detailed task history for Studio-hosted work is kept for 30 days and then becomes unreadable in all copies, including backups. Redaction and disclosure come before any real collection.
- Workspaces run under Coder on Lima virtual machines. Browser chat runs in Open WebUI. Harness approval settings stay in charge, with no second approval layer.
- Access comes over Tailscale and over authenticated internet at studio.jestats.io, with Google sign-in. Backups go to an external drive and encrypted Google Cloud Storage. Failure alerts go to a private Slack channel.
- The shared services budget is up to 100 dollars per month. Hardware and each person's own cloud bills sit outside it.

## Decision questions

### A. What je is

**Q1. The core job.** Should je stay a connection launcher, become the front door that takes a prompt and runs it, or grow into the operator for the whole local stack?
Why it matters. This one call sets the command surface, the routing work, and most of the build order.
Recommendation. The front door, with operator commands under it. A plain `je ask "fix the failing tests"` picks a route and a harness, shows its choice, and runs. The current profile, connect, and doctor commands stay as the explicit layer underneath.
Settled November 4, 2026. Eric chose A. je becomes the front door for a prompt, with operator commands underneath it. This settles the product identity only. Built-in agent scope remained open after this answer. Operator packaging later settled in Q3, the explicit `je ask` syntax in Q4, and layered initial-route authority in Q5.
Provisional implementation note. This is analysis for later questions, not another settled decision. Three architectures fit the front-door identity. A router-as-launcher resolves policy, profile, harness, and model, prints the route, then runs the harness as a child that still owns tools and approvals. A session broker keeps a long-lived je process that owns queues, live sessions, stop and steer controls, and event collection. A je-native agent loop implements its own prompt and tool loop and delegates only selected work to external harnesses. Against the current codebase, the provisional rank is router-as-launcher first, session broker second for jobs and remote control, and je-native loop last except possibly for narrow read-only jobs. The decisive reasons are reuse of the existing LaunchSpec subprocess pattern, preservation of native approvals, a natural route-before-run print, and the smallest new test surface.
Load-bearing assumptions checked November 4, 2026. Headless harness control is plausible from observed help surfaces. Claude Code exposes print mode, model, settings, MCP config, and permission mode. Codex exposes an exec command with prompt, model, config, sandbox, and JSON output. Muse exposes an exec command with provider, model, base URL, config, and approval mode. Route-before-run is supported by the existing separation between profile metadata, doctor checks without the opt-in probe flag, and launch preparation. Local model quality remains the weak point. Help output proves the control surfaces exist, not that a local model can drive tools well. The tested 4B model already failed that bar, so the front door depends on later model qualification rather than on launch plumbing.
Multi-user consequence after Q2. The provisional ranking stays analysis only. Under a trusted group, a router-as-launcher must be identity-aware. Its pre-run display has to name the person and saved profile, the harness and model, any attached memory profile, and where the work will run, meaning the person's own machine or a hosted Studio workspace. It also needs two launch variants with the same route contract. The client-side variant uses profiles saved on that person's machine. The hosted variant runs inside an owned workspace with a scoped, revocable credential and no access to another person's profiles. A session broker becomes more valuable in the hosted case because the operator needs per-person usage, stop controls, and task history, so the gap between the first two architectures narrows. Neither variant may collapse several people into one shared local profile. After Q3, both launch variants belong to the user `je` artifact, including the copy installed inside a hosted workspace. The operator host build creates, starts, stops, and controls those workspaces from the Studio side, and it is not the tool a person uses to run a prompt inside their own workspace. After Q5, every candidate architecture must put initial-route authority in the same layered deterministic policy and show that policy result in the user `je` before launch. A broker may execute or record the result, and a scorer may advise it, but neither becomes the route authority.

**Q2. The first user.** Is the next version built for Eric alone on the Studio, for the small trusted group from day one, or for outside self-hosters?
Why it matters. One user removes accounts, tenant separation, and most access work from the critical path.
Recommendation. Eric first, in a single-operator mode. The multi-person Studio service continues as its own mode behind the same binary, so the trusted group loses nothing and the December path stays short.
Evidence note. The separation machinery is partly proven already. The two-owner workspace trial passed access separation, retained files, stop and start, and revocation cleanup. The onboarding path is not built. Live Google sign-in, the dedicated Google Cloud project, and public DNS, HTTPS, and routing for studio.jestats.io all remain to be created and verified. Choosing A defers exactly that unbuilt onboarding work. Choosing B pulls it onto the December path ahead of model qualification.
Settled November 4, 2026. Eric chose B. The next version is built for the small trusted group from day one, matching the already settled launch audience of two to three trusted people with one or two active at once. Eric remains the operator. Later answers must assume several people from the start, with separate credentials, memory, workspaces, and usage records per person. Onboarding, identity, and remote access are therefore on the critical path rather than deferred. This does not settle packaging, routing rules, memory placement, or the public source timeline.

**Q3. One binary or two.** Q1 settled that operator commands belong under the front door, and Q2 settled that non-operator trusted users install je from day one. The remaining call is packaging and privilege. Should one `je` executable carry gated host commands for every install, or should one codebase ship a user `je` build and a separate operator-only host build?
Why it matters. The standalone Homebrew build already excludes host workspace operation, while the full install includes it. That split exists today without a name. Packaging decides download size, privilege surface, and what a non-operator install can accidentally invoke.
Evidence note. Checked November 4, 2026. The frozen client specification excludes the workspaces and memory service modules, and the installed standalone refuses a workspace status call with a plain message that workspace administration requires a source installation of Studio on the host. The command still appears in help, so the split exists at module level with a dead surface in the user build. This question decides whether that becomes the supported artifact boundary or gets merged back into one gated binary. A follow-up measurement on November 4 found the installed 0.2.0 user executable at 6.9 MB inside a 42 MB Homebrew installation, exposing ten top-level commands in help, including the non-running workspace surface.
Recommendation. Ship split artifacts from one codebase. Every trusted user gets `je` with the front door and client commands only. The Studio alone gets the operator host build for workspace, network, and service control, under a clearly separate name or install flavor with a shared core and versioned compatibility checks.
Settled November 4, 2026. Eric chose A. One codebase ships split artifacts. The user artifact is `je`, the front door and client for every trusted user. The operator-only host build is installed on the Studio alone, under a clearly separate name or install flavor that this decision does not choose. Both artifacts share one core, with versioned compatibility checks between the user client, hosted services, saved profiles, and reviewed model catalogs. Non-operator installs do not carry workspace, network policy, or service-control modules. Whether the user parser later omits host commands entirely or keeps a plain refusal is an implementation detail inside this boundary.

**Q4. The command grammar.** Q1 settled that je takes a prompt at the front door. The remaining call is syntax and guardrails. Should the canonical form be bare text as in `je "fix the tests"`, an explicit verb as in `je ask "fix the tests"`, or both spellings over one implementation?
Why it matters. Bare text is the shortest path from intent to a running local model, and it is also the easiest to trigger by accident or confuse with a subcommand. An explicit verb is clearer in scripts, logs, and documentation.
Evidence note. Checked November 4, 2026. Both a bare prompt and an ask verb fail cleanly in the installed client today with an invalid arguments message and no side effects. The front-door grammar is therefore new surface. Existing subcommand names stay reserved as subcommands, while a prompt after `je ask` cannot collide with them through its first word. The current parser also puts global version and state-directory options before the subcommand and deliberately never echoes invalid arguments back, because an argument may contain a key. The settled explicit grammar keeps that no-echo property and needs a separator only after the verb for prompts that start with a dash. The shipped skills and documentation teach explicit subcommand forms throughout and tell agents to read subcommand help first, so the explicit verb matches the instruction surface that already exists. In a fake-secret canary check the same day, bare text, `je ask`, and a global-flag form with a dash-leading prompt each exited 2 with the same generic invalid arguments message and zero occurrences of the canary.
Recommendation. Support both over one implementation. Make the explicit verb canonical for scripts and docs, and let bare text work interactively only after printing the person and profile, the chosen harness, model, and route, any attached memory, and whether the work runs locally or in a hosted workspace. State-changing operator actions keep explicit subcommands and never hide behind bare text.
Settled November 4, 2026. Eric chose B, explicit verb only, over the recommendation above. The only front-door prompt invocation is `je ask "..."`, in terminals, scripts, logs, and documentation alike. Bare positional text is never parsed as a prompt, interactively or otherwise, and there is no shorthand spelling to support or retire later. Existing subcommands keep their names and meanings, including `je run` for handing a saved connection to another client. A prompt that begins with a dash uses the separator after the verb, as in `je ask -- "..."`. Global options keep their current place before the subcommand. Parse errors keep the current no-echo behavior, so prompt text never appears in an error message. After parsing, `je ask` still owes the identity-aware route display settled in Q1 and Q2 before anything launches. State-changing user and operator commands remain explicit subcommands, and operator commands exist only in the host build under Q3.

### B. Routing between local and cloud

**Q5. Who chooses the route.** When a person runs `je ask`, what has authority to choose the initial harness, model, and execution place? Should a layered declarative policy decide, should a small local classifier decide inside guardrails, or should the person or harness decide each time?
Why it matters. Routing is the main new intelligence in the system, and it has to stay explainable when it picks wrong. With a trusted group, one route can involve operator limits, a person's permitted profiles and cloud access, project privacy labels, harness compatibility, and whether the work runs on that person's machine or in a hosted workspace. The already settled cloud rule bounds this question. Cloud stays bring-your-own and explicitly selected, with no automatic fallback, unless Q6 changes the escalation line.
Evidence note. Checked November 4, 2026. A saved model profile today carries connection facts only under schema version 1, meaning endpoint, key, model, optional context window, and an optional Codex catalog binding. It has no person, role, tier, privacy, cloud allowance, harness preference, or execution-place fields. Every option in this question therefore needs new routing metadata, whether as a profile schema change or a separate policy store. No option routes intelligently from today's saved state alone. There is also a house precedent worth reusing. SkillRoute, Eric's existing local-first routing tool, returns ranked candidates with confidence scores, source evidence, and a replayable trace of inputs, candidates, and scores. Its own examples show modest top confidence, which suits a scored suggestion that policy can accept or reject with reasons. That pattern maps cleanly onto a route display and `je why` without handing the final call to a score. A follow-up probe the same day found that `je why` and `je ask` both exit 2 with the generic invalid arguments message in the installed 0.2.0 client, and `je profile list` reports no saved connections on this machine. The policy engine, routing metadata, and explanation view are therefore future work, not hidden current behavior.
Recommendation. Layered deterministic policy first. Hard constraints filter the candidates, including operator permissions, harness and protocol compatibility, never-cloud labels, and allowed execution places. Soft preferences then resolve the route, with explicit `je ask` flags over project policy over the person's defaults. A local classifier may infer inputs such as task type or model role, but it cannot override a hard constraint or select a cloud route that was not explicitly authorized. The pre-run display and a `je why` view cite the filters and preferences that won.
Settled November 4, 2026. Eric chose A. Layered deterministic policy has authority over the initial route for every `je ask`. Hard constraints filter candidates first and cannot be overridden by flags, project settings, personal defaults, or a scorer. Those constraints include operator permissions for that person, harness, protocol, and catalog compatibility, never-cloud and privacy labels, allowed execution places, and ownership of the selected model and memory profiles. Soft preferences choose only among the surviving routes in this order: explicit `je ask` flags, then project policy, then the person's defaults, then operator-supplied defaults. An optional local classifier or scorer is advisory only. It may see the prompt text, invocation flags, repository path and labels, estimated context size, the person's own defaults, and candidate metadata such as model roles and qualification results. It runs locally only, never through a cloud classifier, and it does not see another person's profiles, memory, usage, or any memory not attached to the requested session. It may return scored task-type or role suggestions with confidence and evidence for policy to consume under deterministic rules. It cannot make the final call, override a hard constraint, select an unauthorized cloud route, or change the route after display. Routing must still work deterministically when the scorer is disabled or unavailable. For the same prompt, bounded metadata, policy version, scorer version, and qualification data, `je ask` resolves the same route. The pre-run display and `je why` cite the policy version, hard filters that removed candidates, the soft preference that won, and any scorer inputs and scores used. This settles initial routing only. Failure, stall, or change of route after launch belongs to Q6. The exact signal set and thresholds stay open in Q7, the role mapping in Q8, and the scorer implementation in Q11.

**Q6. Escalation to cloud.** Q5 settled who chooses the initial route before launch. This question starts only after a local run has begun. It revisits the settled no-automatic-fallback call. When that local run fails or stalls, may je ask the person to approve a cloud continuation, must it stop and leave any cloud run as a new explicit request, or may a preauthorized allowance let it escalate without asking in the moment?
Why it matters. The launch plan forbids automatic fallback for the shared service. The front door still has to decide what happens at the moment a local run fails, and each person's cloud access, budget, and permitted context are separate. Escalation can move prompt, repository, tool, and memory context across a trust boundary, so it is not merely another model selection.
Evidence note. Checked November 4, 2026. The current launcher inherits the harness terminal streams and observes only the child process result, normalized to an exit code, with an interrupt mapped to 130. It cannot see an in-session stall, a tool loop, test failures, or token burn, and real inference-server cancellation remains unqualified in the launch plan. Asking after a nonzero exit is therefore buildable from today's signal alone. Detecting a stall well enough to escalate mid-session needs a supervised or headless event surface that does not exist in the client yet. Continuity cuts the other way than first assumed. Claude Code, Codex, and Muse all expose session resume by identifier in their help surfaces, so a separate explicit cloud run might resume prior context instead of starting cold. Whether a resume under a different profile, model, and protocol route preserves tool and approval state safely is unqualified, and Codex still needs its version-bound catalog to match.
Recommendation. Ask the person first. Stop or pause the local run and show the failure trigger, the target cloud profile and model, the estimated cost, and what context would leave the current machine or workspace. Never-cloud labels stay absolute, and unattended jobs wait and report instead of escalating. Add an optional per-person, per-project allowance later only with hard budget and context caps and only after ask-first evidence shows where it is safe. No operator-wide silent allowance.
Settled November 4, 2026. Eric chose A, ask first, with an explicit usability condition: wanted cloud use must be easy to configure and use. Ask-first therefore cannot mean repeated setup or a grudging cloud path. A person can configure their own cloud profiles, role targets, and defaults ahead of time under Q5, so choosing cloud at the initial route is a single explicit flag, project setting, or personal default that still appears in the pre-run display. For escalation after a local run starts, a person can also preconfigure the target cloud profile, budget ceiling for the estimate and approval display, and context boundary. On a failure trigger, je uses that prepared configuration to present a one-step approval showing the trigger, target profile and model, estimated cost and cap, execution place, and what context would leave. The person approves or declines that escalation in the moment. If no cloud target is configured, je stops with the local diagnosis and a suggested explicit cloud `je ask`; it does not invent a target. Never-cloud and other Q5 hard constraints stay absolute. Unattended jobs wait and report rather than escalating. This answer does not by itself authorize no-ask automatic escalation or a silent fallback. A saved approval may prefill future prompts, and a true standing auto-escalation allowance remains a separate future opt-in only if later design and evidence under Q7 and Q21 prove its triggers, hard caps, notice, and revocation are safe. Cloud configuration must be inspectable, revisable, and removable through the same profile and policy surfaces, must never require a key in an argument, and must show whose cloud account and budget it uses.

**Q7. Routing signals and cloud configuration.** Q5 settled the layered authority, and Q6 settled ask-first escalation with easy explicit cloud configuration. Which concrete signals and configuration fields may feed the initial route and a later escalation approval? Candidates include explicit `je ask` flags, configured cloud intent and target, task type, repository sensitivity, context size, expected cost, latency, current load, model availability, and whether the machine is offline. Escalation triggers are a separate signal family, including nonzero harness exit, a person interrupting to request escalation, supervised timeouts or stalls, and observed token or cost ceilings. Each signal needs a layer, meaning hard filter, soft preference, advisory scorer input, or escalation trigger, plus a source, an owner, and a privacy boundary.
Why it matters. A signal without a readable source becomes folklore, and a sensitivity label without an owner goes stale. Unclassified signals also let a scorer smuggle a soft preference past a hard safety rule. Q6 cannot stay easy if every approval has to rediscover the target, cap, and context boundary by hand.
Evidence note. Checked November 4, 2026. The only context figure je handles today is a model's declared context window. It is validated against the reviewed Codex catalog and passed to harnesses as a maximum. It is not a per-run estimate. Before launch, a launcher can measure prompt length, but the harness assembles the real context from files and history after launch. A context-size signal therefore starts honestly as a prompt-size bucket and explicit flags, with true usage available only after a run if the harness reports it.
Recommendation. Start with a small explicit starter set. Treat operator permissions, compatibility, allowed execution places, offline unavailability, and never-cloud labels as hard filters. Treat explicit task, role, cloud, and execution flags, configured personal or project cloud intent, and estimated context size as soft inputs. Store the escalation target, display budget ceiling, and context boundary as inspectable per-person configuration so approval takes one step. Limit first-release escalation triggers to signals je can actually observe, starting with nonzero exit and an explicit person request, and add supervised stall or token triggers only after an event surface exists. Let inferred task type enter only as a scored advisory input after evaluation. Add cost, latency, and load as decision inputs after the usage ledger can support them per person; before that, show estimates as estimates rather than pretending precision. No per-project policy convention exists in either repo today, so its location and trust rule are part of this answer. A label that travels inside a repository is untrusted input for widening access. It may only narrow a route, as with never-cloud, unless the person or operator has separately trusted that project in their own policy store.
Settled November 4, 2026. Eric chose A. The first routing release uses a small, closed starter set with an explicit layer, source, owner, and privacy boundary for every signal. Hard filters are operator permissions for the requesting person, harness, protocol, and catalog compatibility, ownership of selected model and memory profiles, allowed execution places, candidate availability including offline state, and never-cloud or privacy restrictions. Soft preferences are explicit `je ask` selections, trusted project policy, the person's defaults including configured cloud intent, operator defaults, and a prompt-size bucket. The prompt-size bucket is not a claim about assembled harness context. Authoritative widening policy lives in the person's or operator's policy store, keyed to a trusted project identity. Labels found inside a repository may only narrow a route unless that project has separately been trusted in the authoritative store. Per-person cloud configuration includes the target profile, a budget ceiling used to bound the one-step approval, and a named context boundary. If an escalation estimate is unavailable or exceeds the configured ceiling, it is not presented as a within-configuration one-step approval. First-release escalation triggers are only a nonzero harness exit and an explicit request from the person during or after the local attempt. Stall, elapsed-time, token, and cost triggers wait for a supervised event surface and qualified cancellation. Cost, latency, and load may be displayed as labeled estimates or observed post-run facts, but they do not decide routes until Q21 supplies per-person evidence. Inferred task type does not affect a route in the starter set. A scorer may run locally for evaluation or trace purposes under Q5, but its suggestions remain inert until a later evaluation and an explicit policy change enable them. Unknown or unavailable soft signals are treated as absent rather than guessed, and `je why` names every signal that actually affected the route.

**Q8. Model roles.** Q7 settled that task or role selection starts from explicit flags and defaults, not inference. Should `je ask` expose only two tiers, fast and strong, use named roles with a deliberately small launch set, or adopt a full role taxonomy from the start?
Why it matters. Harnesses already split work across models internally. Roles let policy map each request to the cheapest qualified local model and give Q6 a precise cloud target. Every added role also multiplies model qualification, per-person cloud configuration, and fallback rules. If no qualified local model fills a role, policy must say so rather than silently substitute a different capability.
Evidence note. Checked November 4, 2026. The de facto state is mostly one model. The gateway config exposes a single chat alias, with a comment to keep the same aliases when larger Studio models arrive. A Claude launch maps the default model, model families, and the subagent model all to the one saved profile model. Embeddings are the exception, with their own internal endpoint and embedder in the memory service. Roles at launch therefore mostly name and govern separations that do not exist yet, with embeddings as the one internal role already real. Expressibility also differs per harness. The Claude launch path already sets separate environment slots for the subagent model and four model families, all currently filled with the same model, so an intra-session split has somewhere to land. The Codex path binds one reviewed model per catalog, and Muse resolves knobs per single model and effort tier. On those harnesses, a role choice is a session-level model choice until their own multi-model surfaces prove otherwise.
Recommendation. Named roles with a small launch set. Make fast and strong the user-selectable general roles at launch. Treat embeddings and advisory triage as internal service roles that a person does not select through `je ask`. Add roles such as coder, reviewer, research, or vision only when a named workflow and qualification result justify them. Layered policy resolves the role first, then maps it to a qualified local model. A role may name an optional cloud target only for routes a person has explicitly authorized under Q5, Q6, and Q7. Qualification results, not a scorer's preference, decide whether a model may fill a role.
Settled November 4, 2026. Eric chose A. `je ask` uses named roles with a deliberately small launch set. The only general user-selectable roles at launch are fast and strong. Embeddings and advisory triage are internal service roles and are not `je ask` targets. Policy resolves a role only from the Q7 starter inputs, meaning an explicit selection, trusted project policy, personal default, or operator default, then maps that role to a candidate by person, harness, protocol, and execution place. A local candidate must have a current qualification result for that combination. A role may also name one optional cloud target per person, usable only under the explicit authorization and ask-first rules in Q5, Q6, and Q7. The same physical model may fill more than one role only when it qualifies for each and the route display names the actual model. If no qualified candidate survives, je reports the role as unfilled for that route instead of silently substituting. An explicitly configured substitute is a distinct policy choice and must appear in the display and route trace. Role names stay stable when model assignments change. Claude may use separate main, family, or subagent slots for fast and strong only after each slot is qualified. On Codex and Muse, a role remains a session-level model choice until a multi-model surface is proven. Adding a role requires a named workflow, an owner, qualification evidence, fallback behavior, and any per-person cloud configuration it introduces.

### C. The local runtime

**Q9. Inference engines.** Ollama runs the models today, including the internal embedding path. Q8 settled fast and strong user roles plus internal roles. Should the qualified engine set stay Ollama only through launch, add one MLX-native path, or support several engines per role from the start, including LM Studio and llama.cpp?
Why it matters. Engine choice decides which models, formats, and quantization paths can fill each role at useful speed on Apple silicon. It also multiplies the qualification matrix by role, harness, protocol, and execution place. A model name or an apparently compatible endpoint does not transfer a qualification result across engines.
Evidence note. Checked November 4, 2026 on the development laptop. Ollama is the only candidate engine fully installed and already used by the trials and memory embeddings. The LM Studio command line exists, but no LM Studio application was found in either Applications folder. MLX and mlx-lm are absent from the default command path and default Python, and llama.cpp binaries are absent. Every non-Ollama option therefore starts as a new Studio installation and qualification effort, not as unused capacity waiting on this machine. The matrix arithmetic is concrete. With today's two coding harnesses, two general roles, and two execution places, one engine means eight role assignments to qualify. Adding MLX for the strong role only raises that to twelve. Four engines across both roles reach thirty-two, before any third coding harness multiplies the count again. Internal embeddings stay outside this count on their existing path.
Recommendation. Keep Ollama as the default engine and add one MLX-native path for the strong role on the Studio. Embeddings stay on their existing Ollama path unless a separate qualification moves them. Qualify every role, harness, protocol, engine, and execution-place combination that policy may select, and add no third engine until a named model or workflow requires it. This question settles supported engines and qualification scope, not who installs, starts, or updates them, which belongs to Q10 and Q12.
Settled November 4, 2026. Eric chose C, several engines from the start, over the recommendation above. The supported local engine families are Ollama, an MLX-native serving path, LM Studio, and llama.cpp. Each is a distinct integration and qualification surface, even when two surfaces share an underlying runtime or serve the same underlying model. Support means policy, profiles, discovery, health checks, and route traces can name the engine as part of a candidate. It does not make a candidate selectable. A role assignment becomes selectable only with a current qualification result for the exact person permissions, harness, protocol, engine and its version, model artifact and format, and execution place. Qualification never transfers across engines. Ollama remains the incumbent default and keeps the internal embedding path until a separate qualification explicitly moves an assignment. Engine preference is deterministic policy configuration, not scorer choice. Engine availability is a hard filter under Q7, and an unavailable engine simply removes its candidates. The route display and trace name the engine beside the model. This widened scope accepts the larger qualification matrix recorded above. It does not settle the exact MLX serving implementation, endpoint adapters, model downloads, installation, process startup, updates, or warm-model scheduling. Those stay with Q10 and Q12, with operator-only Studio lifecycle actions respecting the split artifacts in Q3.

**Q10. Model and engine lifecycle.** Q3 split the user `je` from the operator host build, and Q9 made four engine families first-class. Who owns installing engines, pulling or importing model artifacts, pinning versions and digests, benchmarking, qualifying assignments, publishing role mappings, and removing models or engines? Should that lifecycle split by artifact and execution place, stay outside je in native engine tools, or live in every user install?
Why it matters. Qualification exists today as trial scripts and written reports. Productizing it turns every model or engine release into a repeatable evaluation, but lifecycle commands can consume large disk and network budgets and can change what every trusted user may run. A lifecycle action on a person's own laptop has a different authority boundary from one that changes the shared Studio. Downloads and engine installs therefore need explicit ownership, preview, and audit, not merely a convenient verb.
Evidence note. Checked November 4, 2026. The private source currently carries 28 standalone probe and trial scripts beside 15 separate results reports, with results recorded per report rather than in one registry keyed by role assignment. That sprawl worked for one engine and one trial model. Under Q9's four engine families, staying outside je means keeping that manual pattern across every new cell in the matrix, while owning the lifecycle is mainly a consolidation of machinery that already exists in script form. Storage makes the preview requirement concrete. ### F. Trust, privacy, and operations
