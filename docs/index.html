je is the client for J&E Studio. It saves your connections and helps your existing tools use them. The Studio service is private and operator-managed. Installing the client does not create an account or grant service access.

Two clients share the je name. This page documents the standalone Homebrew client first. A separate Python client lives in the private Studio repository and carries a few commands the standalone client does not have yet. Where a feature belongs to only one of them, this page says so. Start with Routes & models for the split in one place.

01

Install once. Start where you are.

je ships as a signed and notarized native binary for Apple silicon Macs. Homebrew installs it with one command. There is no Python to manage and no source checkout to keep.

brew install jestatsio/tap/je
je --version

The version command prints je 0.3.2, the current release. From there the path to your first session stays short.

  1. Set up your tools. Run je setup to add the Studio plugin to Codex or Claude Code. Setup guide
  2. Save your connection. Your operator gives you an endpoint, a model name, and a personal key. Save a connection
  3. Open a session. Start working in the client you already know, inside your project. Client sessions

Install Codex, Claude Code, or Ollama separately. je works with the clients you have and installs none of them for you.

i
Upgrading from 0.2.0

Run brew upgrade jestatsio/tap/je. The native client replaces the Python build in place and your saved profiles still load. New profile writes store keys in macOS Keychain instead of in the profile file, and je profile migrate moves an older embedded key after a no-inference check. Release notes ↗

03

Save your personal connection.

A profile gives a service endpoint, model, and personal key a name you can use again. Replace the example address and YOUR_MODEL_NAME with the values from your operator.

je profile add studio \
  --endpoint https://models.example.test \
  --model YOUR_MODEL_NAME

je doctor --profile studio

The client asks for your key privately in the terminal. Keep the key out of command arguments. The default connection check verifies authentication and model availability without generating a response.

↗
One profile per tested route

Claude Code and Codex use different model protocols. A working model listing does not establish compatibility with either client. Use the route and profile settings your operator has tested for your chosen tool.

List your profiles with je profile list, or inspect one with je profile show studio. Neither command displays its key. To update a profile, repeat je profile add with --replace.

Work in your own environment

A Studio session, in a familiar client.

Open a terminal in the project you want to work on. The launcher applies your saved connection to that session while keeping the client's own tools, instructions, and approval controls.

Claude Code

Use a profile with a Claude-compatible route enabled by your operator.

je connect claude --profile studio

je checks the connection and supplies temporary session settings. If an existing sign-in or provider conflicts with that route, the launch stops so you can resolve it.

Codex

Use an operator-tested Responses route and a reviewed model catalog matched to the exact installed Codex version and configured context limit. Replace every uppercase placeholder below.

je profile add studio-codex \
  --endpoint https://models.example.test \
  --model YOUR_CODEX_MODEL \
  --context-window CONTEXT_TOKENS \
  --codex-catalog /absolute/path/to/reviewed-catalog.json \
  --codex-version YOUR_CODEX_VERSION

je connect codex --profile studio-codex

At launch, je checks the executable version, catalog contents, selected model, and context against the saved binding. Changing the profile's context does not enlarge the server's limit. A generic model route is not a qualified Codex connection.

Pass additional supported client arguments after --. If a client cannot be found, use --executable /absolute/path/to/client. Organization-managed settings may restrict custom providers.

For one prompt without a full client session, je ask selects a qualified assignment, shows the full route, and runs the prompt only through that route. je why shows the same choice without running anything. Assignments and their qualification evidence are covered in Routes & models and the command reference.

Desktop apps, editors, and other clients

Generate configuration fragments for review with je export. Exporting does not activate or replace an app's settings. Read the generated README and confirm compatibility with the app's installed version.

je export --profile studio

For another client that reads OpenAI environment variables, use je run --profile studio -- COMMAND. This passes the connection to the child process. It does not translate protocols or attach shared memory.

Local first, cloud by choice

Routes and models.

Every route is explicit. You name the profile or assignment for each session, and there is no automatic fallback between local and cloud in either client. When no qualified route survives policy, je stops and says so instead of substituting a different capability.

Standalone client Assignments and the models inventory

In the Homebrew client, classification lives on assignments: each published assignment carries a provider kind (local or cloud) and a role (fast or strong). je ask resolves one qualified assignment through layered policy and shows the person, profile, harness, model, and place before anything runs. Cloud use there follows the saved policy you configured, shown by je policy show; the route display names it every time.

je models
je assignments list
je why --role fast -- "summarize this change"

je models in this client is a read-only local inventory: engines found on your machine, published model artifacts, your assignments and their qualification status, and storage use. It does not contact a gateway, and finding an engine on PATH does not mean it is healthy or qualified. Route metadata never carries a secret; profiles hold a secret reference while the key itself stays in macOS Keychain.

Python client Classified profiles and route status

In the Python client from the private Studio repository, classification lives on the profile instead: save each connection with --location local or --location cloud and, when you know it, --tier fast or --tier strong.

je profile add studio-fast \
  --endpoint https://models.example.test \
  --model YOUR_FAST_MODEL \
  --location local \
  --tier fast

je models list
je models status

je models list reads only your saved profiles and shows the inventory without contacting any gateway. je models status checks authentication and model availability for every route without generating a response. Neither command establishes task quality, picks a route for you, or enables fallback. Keys are never printed and are rejected from public route metadata. The standalone client above does not have models list or models status; its single je models command is the local inventory just described.

Reuse a setup, compare honestly

Task presets and route comparisons.

Python client Everything in this section lives in the Python client from the private Studio repository today. The standalone Homebrew client does not have je task, je runs, or je compare yet, and this section does not claim otherwise.

Task presets

A preset saves one repeatable setup: a harness (Codex or Claude Code), a default profile, an optional memory connection, an optional project directory, and optional harness arguments. Preset files are owner-only, and their argument lists may contain prompts, so treat them as private.

je task add coding \
  --harness codex \
  --profile studio-fast \
  --directory /absolute/path/to/project

je task run coding -- exec "Fix the selected regression"
je task run coding --profile cloud-strong --allow-cloud

Override the route for one run with --profile without rewriting the preset. Any task launch that selects a profile marked cloud also needs --allow-cloud, every time, whether the cloud profile is the preset default or an override. That gate covers task and comparison launches; a direct je connect session opens the profile you name. Native harness approvals stay in control in every case.

Run history, metadata only

Each task run leaves a small local record: the task, harness, profile, model, start and finish times, duration, and process outcome. Records never contain prompts, arguments, working directories, endpoints, transcripts, tool output, or credentials, and usage and cost stay honestly unknown rather than estimated. A harness exit code is a process result, not a quality score.

je runs list
je runs show RUN_ID
je runs remove RUN_ID

Run records have no automatic expiry, so remove them yourself when they stop being useful. Removing a record changes only that local metadata; your client's own history and any provider logs stay untouched.

Route comparisons

A comparison runs the same declared work through several routes you select explicitly, from a local JSON manifest of cases. Each case names a harness, its arguments, and a per-case timeout, and may add a fixture directory and an independent verifier command.

je compare run suite.json \
  --profile studio-fast --profile cloud-strong --allow-cloud
je compare list
je compare show COMPARISON_ID

Every case and route pair gets a fresh private copy of the fixture, and the source fixture is never the working copy. The verifier runs only after the harness succeeds, without the model or memory credentials, and its result is reported separately from harness completion: a case with no verifier is unverified, never a quiet pass. Timeouts bound each harness and verifier process. Comparison records are metadata only, like run records. One comparison run is evidence about those cases on that day, not a general model ranking.

Context you control

Keep useful knowledge between sessions.

Studio memory holds preferences and project facts across connected tools, separately for each person. Use the Studio memory page to inspect saved information, edit it, review earlier versions, or decide what to forget.

Memory is optional and uses a separate personal token. Save the complete MCP endpoint supplied by your operator, including its path.

je memory add studio-memory \
  --endpoint https://memory.example.test/mcp
je memory check studio-memory

je connect claude --profile studio \
  --memory-profile studio-memory

The check lists available tools without reading saved memories or requesting inference. Saving a connection does not attach it automatically. Select --memory-profile for each supported session.

i
Current memory support

Saving is proposals-only by design: a model may propose a memory, and you accept it explicitly. Automatic saving stays off by default, because current small models still choose the wrong edit often enough to need your review. Codex attachment uses its own tested model profile and Codex version pairing from your operator. Native Ollama and desktop exports do not attach memory through this client.

Deleted memories leave recall immediately and remain in trash for 30 days. Removing a local memory connection does not delete saved memories or revoke the service token.

Native command-line chat

Use Ollama with its own connection.

The native Ollama CLI uses a separate endpoint, model name, and personal key. Install Ollama separately and request these values from your operator. A model gateway profile is not a substitute.

je ollama profile add studio-native \
  --endpoint https://native.example.test/ollama \
  --model YOUR_NATIVE_MODEL

je ollama --profile studio-native check
je ollama --profile studio-native

Use the complete native API root, including any /ollama prefix. Do not append /api or use the gateway's /v1 endpoint. The check lists authorized models without starting inference.

During a session, a temporary loopback relay supplies the saved credential upstream and closes when the CLI exits. Global Ollama routing settings stay unchanged. The shared connection supports chat and model inspection. Model downloads and management remain the operator's responsibility.

This integration covers the native CLI. It does not configure the Ollama desktop app or attach shared memory.

What the evidence actually says

Harnesses and qualification.

The launch harness set is settled: Codex, Claude Code, and Muse. A harness earns a route one recorded qualification at a time, for an exact model, engine, protocol, launch mode, and place. A model listing, a doctor check, or success in a different harness never transfers.

Today exactly one of the 112 launch-matrix cells is qualified: the narrow built-in single-step path with one small local model on a personal machine. Everything else is honestly planned or, for 24 Muse cells on non-MLX engines, declared unsupported ahead of qualification from trial evidence. Print the matrix yourself any time:

je support-matrix
je status

Probed, not launched: Pi and OpenCode

Two further harnesses, Pi and OpenCode, were probed through the same adapter contract on November 13, 2026, as discovery evidence only. A bounded Pi trial then passed for one exact assignment: Pi 1.5.2 in RPC mode, inside a Docker boundary, driving one small local model, fixed its test bug unaided, and passed independent verification. That result comes with its limits attached. It is one run, one task, one small model. Pi has no native approval prompts, so safety in that trial came from the outer Docker boundary, not from approval parity with Codex or Claude Code. The trial adds nothing to the launch set above, and this page claims nothing more general from it. The full records are PI_TRIAL.md, PI_DISCOVERY.md, and OPENCODE_DISCOVERY.md in the je repository.

The same small model did not qualify for the coding workflow through Codex or Claude Code, and it fills neither the fast nor the strong role. Final model selection waits for the Studio hardware and its own recorded trials.

Know what is saved

Personal credentials. Explicit access.

On your computer

Keys and tokens are saved in macOS Keychain through the bundled je-secret-helper. Profile files hold public fields and a secret reference, never the key itself. Profiles saved by 0.2.0 with an embedded key still load under strict private-file checks. Model, memory, and native Ollama profiles are separate.

In your session

You choose the profile and whether to attach memory. Native client instructions, hooks, history behavior, and approval controls still apply.

At your Studio

Your operator manages service access, logging, and retention. Confirm those policies before sending sensitive material. The public client does not provide a Studio account.

Usage and run records

The standalone client's je ask keeps a content-free usage trace on your machine: route, harness, role, timing, reported token counts, and outcome, with no prompt or answer text. The Python client's run and comparison records follow the same rule. They hold route, task, timing, and process metadata only, and never contain prompts, raw arguments, working directories, endpoints, fixture or manifest paths, generated artifacts, transcripts, tool or verifier output, or credentials. Task preset files are the one private exception to know about: their argument lists may contain prompts you wrote there, and they stay in owner-only files on your machine.

Where profiles live

The default directory remains ~/.config/je-gateway for compatibility, or je-gateway under XDG_CONFIG_HOME. Existing profiles do not need to move.

SettingPrecedence
je --state-dir PATH …An explicit command-level location takes precedence.
JE_STUDIO_HOMEThe preferred environment override.
JE_GATEWAY_HOMEThe legacy override, used when JE_STUDIO_HOME is unset.

For noninteractive model setup, use --key-file with an owner-only regular file or --key-env naming an already-set environment variable. Memory setup uses --token-file or --token-env. Never put a credential's value directly in a command argument.

Keep your setup current

Updates and a clean way out.

Update the client

brew update
brew upgrade jestatsio/tap/je

Studio plugins update through each client's native plugin manager. Check the release notes before upgrading. A Codex version change may require a newly reviewed catalog and an updated profile binding.

Remove the client

je setup --remove
brew uninstall je

Remove the plugins before uninstalling the command-line client. Your saved profiles and native marketplace entries remain. Removing a profile, plugin, or local installation does not revoke a server credential. Ask your operator to revoke access when needed.

When something needs attention

Start with the connection.

Setup cannot find Codex or Claude Code

Install the native client separately and confirm its command works in your terminal. Run je setup --dry-run to inspect detection, then try setup for that client. Setup does not download the client for you.

The key is rejected or the model is missing

Run je doctor --profile NAME and confirm the endpoint and permitted model name with your operator. Inspect the saved values with je profile show NAME. Replace the profile explicitly if its key or connection has changed.

Codex reports a version or catalog mismatch

Match the installed Codex version, model, context limit, and reviewed catalog to the saved profile. Ask the operator to review changed catalog contents before replacing the binding. A successful model listing does not remove this requirement.

Memory is saved but not available in the session

Run je memory check NAME, then launch a supported client with --memory-profile NAME. Saving a connection or installing the plugin does not attach memory automatically. Verify the supported Codex pairing when using Codex.

Ollama cannot find the expected model

Check the separate native profile with je ollama --profile NAME check. Use the operator's native model name and full API root. Gateway aliases and gateway credentials do not automatically work with the native service.

A desktop export has not changed the app

That is expected. Exports create files for review, without activating them. Read the generated README and apply only the relevant settings through the app's supported configuration workflow.

A command on this page is missing from your je

Check the tag beside the section heading. Commands marked Python client, such as je models list, je task, je runs, and je compare, live in the Python client from the private Studio repository and are not in the Homebrew build yet; the standalone client answers them with its short invalid-arguments message. Commands marked Standalone client, such as je ask and je assignments, are the reverse. Run je --help to see exactly what your build offers.

For a connection problem, contact your Studio operator. For a client issue, open an issue with the command, installed versions, and error text. Leave out credentials and private memory contents.
